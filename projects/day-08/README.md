# День 8. Работа с токенами

Агент с полной историей и инструментами измеряет размер нового вопроса, истории,
входа API и ответа, а также фактическую стоимость обращений. Три независимых
сценария показывают короткий диалог, длинный диалог и попытку переполнить контекст.

## Модель и токенизатор

Для эксперимента выбрана `qwen/qwen-2.5-72b-instruct` через Polza.ai. У неё есть
опубликованный токенизатор, а проверенный каталог указывает окно 32 768 токенов:
переполнение проверяется без создания миллионного контекста DeepSeek из прошлых дней.
Точное `context_length` скрипт читает из `/api/v1/models` при каждом запуске
и записывает в отчёт. Поддержка `tools` и `tool_choice` проверяется в параметрах
модели или её `top_provider`. Если модель или длина контекста не найдены,
эксперимент не запускается с придуманными значениями.

Локально используется официальный `tokenizer.json` и шаблон сообщений из
`Qwen/Qwen2.5-72B-Instruct`, ревизия `495f393`.
Скачиваются только файлы токенизатора, **не веса модели**. Они кешируются вне
репозитория в `~/.cache/ai-advent-challenge/`. Библиотеки — `tokenizers` и Jinja2;
устанавливать PyTorch или запускать модель локально не нужно.

Локальный подсчёт — точный для выбранного токенизатора и нашего шаблона. Это
**оценка входа сервиса**, поскольку провайдер может иначе оформить сообщения
и схемы инструментов. Фактический оплаченный вход берётся из `usage` API.
Разница между этими числами сохраняется как два отдельных значения; искусственно
подгонять одно под другое код не пытается.

## Что считается

| Показатель | Как получаем |
| --- | --- |
| Вопрос локально | Токенизируем только текст последнего вопроса пользователя, без роли и шаблона |
| История локально | Считаем все сообщения перед добавлением этого вопроса: system, user, assistant, tool; со стандартным шаблоном, без схем tools |
| Весь вход локально | Текущие messages, схемы tools и префикс генерации по официальному шаблону |
| Вход API | `usage.prompt_tokens` конкретного HTTP-запроса |
| Выход API | `usage.completion_tokens`, включая генерируемые вызовы функций |
| Всего API | `usage.total_tokens` |
| Текст ответа локально | Токенизируем текст content; аргументы tool_calls сюда не входят |
| Кеш API | `usage.prompt_tokens_details.cached_tokens`, если указан |
| Стоимость | `usage.cost_rub`, либо его алиас `cost`, один раз |
| Накопленный расход | Суммируем вход, выход и стоимость всех обращений этого сценария |

Если одного вопроса недостаточно для завершения задачи и модель запрашивает
инструмент, учитывается каждый HTTP-шаг. Токены результата Python-функции попадут
во вход следующего обращения; сама локальная функция не генерирует токены LLM.

Размер сохранённой истории не равен общему расходу. Одна и та же история повторно
отправляется при следующих обращениях. Число токенов нового вопроса и истории также
не обязано точно складываться во вход API: есть шаблон, tools и служебные токены.

Отсутствующие метрики обозначаются `н/д`, а не нулём. Если хотя бы у одного обращения
нет стоимости, итоговая стоимость неизвестна; известные части не выдаются за полный
расход. Кешированные токены входят во входные, повторно их не прибавляем.
Падение цены из-за кеша может нарушить простой рост стоимости вместе с контекстом.

## Три сценария

| Сценарий | Что происходит |
| --- | --- |
| `short` | Два вопроса: конвертация 250 USD и добавление 1500 RUB, с общей историей |
| `long` | Те же первые два вопроса, затем шесть заметок примерно по 1200 локальных токенов и вопрос о первоначальных суммах: всего девять пользовательских ходов |
| `overflow` | Реальный диалог: те же первые два вопроса, контрольная метка, затем заметки примерно по 2400 локальных токенов с настоящим ответом модели на каждую; продолжаем до отказа API |

Каждый сценарий начинается с чистой собственной историей. В длинном диалоге ответы
на заметки тоже получаются от модели и входят в расходы. Первые два вопроса
совпадают с коротким сценарием, но ответы и роутинг сервиса могут различаться.

В переполняющем сценарии **все ответы assistant получаются от LLM**. Скрипт
автоматически готовит пользовательские вопросы и заметки, но не записывает
в историю придуманные ответы модели. Каждый новый ход проходит через обычный
`Agent.run`: HTTP-запросы, выполнение выбранных инструментов, ответ и сохранение
контекста. Токены и стоимость всех подготовительных обращений включаются в отчёт.

История растёт постепенно, а запрос, который перестанет помещаться, определяется
реакцией сервиса. Скрипт не блокирует его своей локальной проверкой. Поэтому можно
увидеть рост входа и расходов до последнего успешного хода и первый отказ API.
Точное число ходов зависит от окна контекста, ответов и правил провайдера.

Если сервис продолжает принимать диалог даже после того, как локальная оценка
превысила `context_length` на 4096 токенов или 20% окна (что больше), отправляется
последний вопрос о контрольной метке и сценарий завершается. Это ограничивает
эксперимент при неожиданном поведении провайдера; такой исход не объявляется
доказанным отказом из-за переполнения.

## Запуск

```bash
cd ~/Projects/ai-advent-challenge
source .venv/bin/activate
python -m pip install -r projects/day-08/requirements.txt
```

Сначала подготовка без генерации и расходов на обращения к LLM:

```bash
python projects/day-08/main.py --prepare
```

Она читает каталог и скачивает токенизатор с Hugging Face при отсутствии в кеше.
Проверяет токенизацию короткой строки и при успехе завершается с кодом 0 без
демонстрационного вывода. Нужен доступ к обоим сервисам; `POLZA_API_KEY` берётся
из корневого `.env`.

Затем по очереди:

```bash
python projects/day-08/main.py --scenario short
python projects/day-08/main.py --scenario long
python projects/day-08/main.py --scenario overflow
```

Ответы и метрики сохраняются в файлы; демонстрационный вывод в консоль удалён.
Автоматических повторных попыток нет. Таймауты: соединение 10 секунд, чтение 180.
Модель запрашивает инструменты автоматически, температура 0, предел 8 обращений
на вопрос. При ошибке сценарий останавливается, полученные данные сохраняются.

## Результаты и история

Результаты всех сценариев собраны в двух файлах:

- [results.txt](results.txt) — вопросы и ответы обычным текстом, при сбое — описание ошибки;
- [metrics.txt](metrics.txt) — таблицы по каждому HTTP-обращению, накопленные расходы
  и исходный ответ API при ошибке.

Каждый прогон записывается отдельным разделом с названием сценария. Новые запуски
дописываются в конец; накопительные суммы считаются внутри каждого прогона.
Обновление текущей таблицы не заменяет разделы предыдущих прогонов.

Полные контексты `history-short.json`, `history-long.json`, `history-overflow.json`
остаются локальными рабочими файлами и не включаются в MR.

В отчёт также записываются лимит из каталога, ревизия токенизатора и фактические
модель/провайдер, если сервис их вернул. Ключ API не записывается. Новый запуск того
же сценария создаёт чистую историю; предыдущая история копируется в соседний
`ai-advent-challenge-archive/day-08/`, вне репозитория. Текстовые результаты сохраняются.

## Что проверяем при переполнении

`max_tokens=512` ограничивает **выход**, а не задаёт новое окно контекста модели.
Во всех сценариях значение одинаковое. Для проверки переполнения увеличиваем
историю, а не уменьшаем лимит ответа. Сервис может учитывать и резерв под ответ.

| Наблюдение | Что означает |
| --- | --- |
| HTTP-ошибка с сообщением о длине контекста | Вход отвергнут; фиксируем точный статус и исходный ответ |
| Успешный ответ на подготовленный большой вход | Отказ не подтверждён; проверяем usage, ответ и заявленный лимит, не объявляем это ошибкой переполнения |
| `finish_reason=length` | Обрезана генерация по выходному лимиту; это отдельная ситуация, не доказательство переполнения входа |
| Ошибка сети, квоты, баланса или tools | Не считается переполнением только потому, что произошла в сценарии overflow |

При HTTP-ошибке программа завершится с кодом 1 — в стресс-сценарии это ожидаемая
возможность, причина остаётся в отчёте. При отсутствии usage стоимость попытки
считается неизвестной, а не автоматически нулевой. Ни историю, ни схемы инструментов
код автоматически не обрезает.

### Рост контекста и цены

| Момент длинного диалога | Новый вопрос локально | История до вопроса локально | Весь вход API | Выход API | Цена этого обращения, ₽ | Накопленная цена, ₽ |
| --- | --- | --- | --- | --- | --- | --- |
| Первый вопрос, первый HTTP-шаг | 39 | 188 | 1774 | 66 | 0,07847267 | 0,07847267 |
| Первая заметка | 1257 | 653 | 3616 | 5 | 0,15383965 | 0,60627757 |
| Третья заметка | 1257 | 3197 | 6160 | 5 | 0,26190595 | 1,07605632 |
| Шестая заметка | 1257 | 7013 | 9976 | 5 | 0,42400538 | 2,18597303 |
| Финальный короткий вопрос | 50 | 8285 | 10 041 | 49 | 0,42884326 | 2,61481629 |

Текст каждой заметки имеет одинаковое число локальных токенов, ответ «Принято.»
занимает 5 выходных токенов API. Тем не менее вход растёт на 1272 токена при каждом
таком ходе: предыдущий разговор отправляется снова. Финальный вопрос короткий,
но оплачивается весь вход, а не только его 50 локальных токенов.

Локальная оценка и API существенно различаются. В первом запросе — 607 против
1774, в финале длинного диалога — 8715 против 10 041. Локальные значения проверены
повторным подсчётом сохранённых сообщений официальным токенизатором. На участке
заметок длинного диалога разность стабильна: 1326 токенов. Причина полного
расхождения на стороне сервиса не установлена; не считаем эту разность доказанным
размером какого-либо конкретного внутреннего промпта. Для расходов используем usage,
для локальной оценки окна оставляем эту погрешность явной.

В коротком и длинном прогоне модель сначала передала калькулятору строку
`get_exchange_rate_result` вместо числа. Проверка схемы вернула ошибку, затем
модель вызвала калькулятор с числом 90. Итоги верны, но эти реальные ошибки и шаги
исправления сохранены в историях и включены в метрики.

### Что произошло на границе окна

| Попытка | Вход локально | Вход по API | Результат |
| --- | --- | --- | --- |
| Последняя успешная в основном прогоне | 30 447 | 31 723 | HTTP 200, «Принято.» |
| Следующая заметка | 32 927 | Не вернулся | HTTP 400, BAD_REQUEST, «Некорректный запрос.» |
| Контроль с тем же отклонённым вопросом и меньшей историей | 30 447 | 31 723 | HTTP 200, «Принято.» |
| Повтор исходного большого запроса с полной историей | 32 927 | Не вернулся | Повторно HTTP 400, BAD_REQUEST |

Окно в каталоге — 32 768. В последнем успешном запросе даже сумма фактического
входа и запрошенного резерва ответа 512 составляет 32 235. Локальная оценка
отклонённого запроса уже больше окна, ещё без поправки на наблюдаемое расхождение.

Для контроля взяли исходный `history-overflow.json`, удалили только одну завершённую
пару «Заметка 12 → Принято», сохранили последний вопрос (заметку 13), модель, tools,
температуру и `max_tokens=512`. Новый запрос был принят. Его метрики и ответ сохранены
отдельно; исходный неудачный прогон не изменён.

Затем полностью повторили исходный большой запрос. Сохранённый массив messages
совпадает с исходной неудачной попыткой, параметры модели не менялись. Сервис снова
вернул HTTP 400, без usage. Получена последовательность **большой → отказ,
уменьшенный → успех, большой повторно → отказ**.

Установлено, что исключение одной пары сообщений изменило результат с отказа
на успех, а повтор полной истории снова получил отказ. Это согласуется с гипотезой
переполнения контекста. Однако API-ответы не содержат явного кода
`context_length_exceeded`; точная внутренняя причина сервером не раскрыта.
По этим данным нельзя однозначно отделить лимит токенов модели от другого
ограничения размера запроса в сервисе или у провайдера.
Зафиксированы `BAD_REQUEST` и trace_id `bb4b4568-5c6d-4c4a-99a5-88374cb5b0d8`
для исходного отказа, `2f8d2630-cfba-4256-a4c9-b8417ac3d5ca` — для повторного.

В наблюдавшемся отказе API не вернул сообщение assistant. Не установлено,
на каком внутреннем этапе обработки произошла ошибка. Агент сохраняет текущую историю с последним пользовательским
вопросом и записывает ошибку. Автоматического удаления старых сообщений или повторной
попытки нет. Это отличается от `finish_reason=length`, которого в прогонах не было.

2. **Размер одного входа и накопленный расход надо учитывать отдельно.** Последний

   само по себе не изолирует влияние истории: число вопросов и HTTP-обращений тоже разное.
3. **Наш локальный подсчёт не воспроизвёл входные метрики сервиса.** Первый запрос:

4. **Отказ большого контекста воспроизведён, его точная серверная причина неизвестна.**
