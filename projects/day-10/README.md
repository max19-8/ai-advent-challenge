# День 10. Сравнение стратегий управления контекстом

Один агент с переключателем `--strategy window|facts|summary`. Модель —
`qwen/qwen-2.5-72b-instruct` через Polza.ai, температура 0. Используем сценарий
и десять эталонных деталей из дня 9. Ниже приведены результаты реального прогона.

## Как работает агент

`Agent` в `agent.py` отвечает за цикл обработки пользовательской реплики:

1. Стратегия обновляет память перед ответом, если это требуется.
2. Агент собирает system, память, недавние сообщения и новый вопрос.
3. HTTP-клиент отправляет запрос и получает ответ модели.
4. Стратегия добавляет пару user/assistant и при необходимости обрезает или сжимает историю.

В основной сценарий каждой стратегии поступают одни и те же 12 пользовательских
реплик, но ответы генерируются заново с её текущей памятью: 24 сообщения на диалог.
Это три настоящих диалога, а не три представления одной записанной истории.
Ответы модели могут различаться; сравнение относится к этим конкретным прогонам.
Инструменты здесь не используются, чтобы отдельно проверить управление текстовым контекстом.

### Sliding Window

`Window` хранит последние **6 сообщений**, то есть 3 полные пары user/assistant.
После ответа старые сообщения отбрасываются из рабочей памяти. Дополнительных
вызовов LLM нет. System и новый вопрос добавляются отдельно, не входят в эти 6.

Полный журнал диалога сохраняется локально для анализа, но агент не читает его
при сборке контекста: он не служит скрытой памятью.

### Sticky Facts / Key-Value Memory

`StickyFacts` перед **каждым обычным пользовательским сообщением** вызывает LLM
с прежними фактами и новой репликой. Модель возвращает полный JSON-объект
«ключ — строковое значение». Схема ключей не содержит готовых эталонных ответов:
модель сама выбирает ключи и извлекает значения из разговора. Код проверяет типы
и непустые строки. Невалидный JSON останавливает этап без автоматической платной попытки исправления.

Позднее исправление должно заменить прежнее значение того же факта. Если новых
данных нет, модель должна вернуть прежний словарь. Сохранение сведений проверяем
по реальным обновлениям: корректность семантики не гарантируется одной проверкой JSON.

Запрос основного ответа: `system + facts + последние 6 сообщений + новая реплика`.
В локальном checkpoint facts хранятся отдельно от массива истории. В читаемых
результатах словарь представлен строками «ключ: значение».

### Summary

`Summary` использует механизм дня 9: обновление через **10 новых сообщений**,
после обновления остаются последние **6 сообщений**. Между обновлениями хвост
временно растёт. Для обновления модель получает предыдущую сводку и вытесняемый
фрагмент. Перед проверкой деталей выполняется заключительное сжатие остатка.

После 10, 20 и 24 сообщений сводка покрывает соответственно 4, 14 и 18 сообщений.
В отличие от эксперимента дня 9, здесь она используется уже во время основного
разговора. System одинаков для трёх стратегий; правила обновления summary сохранены.
Пределы ответа: обычный ответ — 128, summary — 384, facts — 768 токенов.
Пустые и обрезанные ответы, включая служебные, не принимаются как успешные.

## Сценарий и проверочные детали

Обсуждаем подготовку учебного вебинара. Детали вводятся постепенно; бюджет сначала
предварительный, затем исправляется. `FACTS` в `main.py` содержит эталоны только
для нашей ручной проверки. Значения не подставляются в запросы извлечения фактов,
суммаризации или проверочные вопросы.

| Деталь | Актуальное значение |
| --- | --- |
| Ответственная | Алина Ветрова |
| Срок подготовки | 20 декабря 2026 года |
| Бюджет | 42 000 рублей, вместо предварительных 30 000 |
| Ограничение | Запись вебинара запрещена |
| Формат | Только онлайн, без очного участия |
| Участники | 18 |
| Начало | 19:30 по московскому времени |
| Продолжительность | 90 минут |
| Платформа | Контур.Толк |
| Материалы | Один PDF-файл, без видео |

После основного разговора создаётся checkpoint. `Agent.probe()` задаёт десять
вопросов к одной и той же замороженной памяти. Он не добавляет вопросы и ответы
в историю и не запускает обновление facts или summary. Это специальная проверка
чтения памяти, а не продолжение обычного диалога. Ответы не подсказывают друг другу.
Правильность оцениваем по смыслу вручную, без LLM-судьи и жёсткого сравнения строк.

## Checkpoint и независимые ветки

Checkpoint — полная копия состояния агента: стратегия, сообщения, facts либо
summary, а также счётчики её обновления. Контрольный хеш позволяет обнаружить
изменение исходного checkpoint между этапами.

`Branches.fork()` создаёт два отдельных файла состояния из одного checkpoint.
`switch()` загружает выбранную ветку с диска, `ask()` продолжает её и сохраняет
изменения только в её файл. Последняя выбранная ветка также записывается на диск.
Обычный `ask()` в ветках использует ту же стратегию, включая обновления facts.

Для каждой стратегии демонстрация выполняется автоматически:

1. В A меняем бюджет на **50 000 рублей**, срок — на **22 декабря 2026 года**.
2. Переключаемся на B от исходного checkpoint: бюджет **35 000 рублей**, срок —
   **18 декабря 2026 года**.
3. Переключаемся **A → B → A**, каждый раз спрашиваем бюджет и срок.
4. Отдельно спрашиваем исходный checkpoint о бюджете и сроке.
5. Проверяем, что чтение веток не изменило их сохранённые состояния и checkpoint.

Исходные эталоны checkpoint — 42 000 рублей и 20 декабря. У Sliding Window эти
сведения уже находятся за пределами окна и могут быть недоступны. Неизменность
checkpoint проверяем по состоянию, а способность восстановить старые сведения —
по ответам отдельно. Отсутствие старого факта у window само по себе не означает смешение веток.
В демонстрации каждая ветка получает 4 новых сообщения; порог 10 новых сообщений
для очередного summary ещё не достигается. Проверка не доказывает работу всех
возможных длин веток или всех порядков обновления памяти.

## Запуск

Подготовка в новом терминале:

```bash
cd ~/Projects/ai-advent-challenge
source .venv/bin/activate
python -m pip install -r projects/day-10/requirements.txt
python projects/day-10/main.py --prepare
```

Используется корневой `.env` с `POLZA_API_KEY`. Подготовка проверяет наличие модели
в каталоге и локальный токенизатор, не запрашивает генерацию. Токенизатор Qwen2.5
72B с ревизией `495f393` используется из кеша дней 8–9; веса модели не скачиваются.

Затем выполняем по одной команде, дожидаясь завершения:

```bash
# Три основных диалога: window, facts, summary
python projects/day-10/main.py --strategy all --stage dialogue --new

# По десять вопросов каждой стратегии
python projects/day-10/main.py --strategy all --stage probe

# Создание, продолжение и переключение веток для каждой стратегии
python projects/day-10/main.py --strategy all --stage branches
```

Можно запускать тот же этап отдельно для одной стратегии, заменив `all` на
`window`, `facts` или `summary`. По умолчанию выбрано `all`.
Вопросы, ответы и обновления памяти сохраняются в `results.txt`, расходы — в
`metrics.txt`. Подробного вывода в консоль при успешном запуске нет. Ошибки
сообщаются в терминале; демонстрационный вывод после эксперимента удалён.

`--new` разрешён только с `dialogue`: архивирует локальное состояние выбранной
стратегии, её ответы и usage в соседний `ai-advent-challenge-archive/day-10/`.
Другие стратегии остаются на месте. Завершённый, прерванный или неуспешный этап
повторно не запускается молча. Автоматических повторов HTTP-запросов и возобновления
частично выполненного этапа нет. При ошибке сначала анализируем уже сохранённые данные.
При `all` стратегии выполняются последовательно; ошибка останавливает команду.
Если первые стратегии завершились, а следующая упала, не перезапускаем все с `--new`
без разбора: это создаст новые оплаченные диалоги.

## Расходы и сложность

По данным API отдельно показываем вход, выход, кешированные токены и стоимость.
Суммарные токены — вход плюс выход, кешированные повторно не прибавляются.
Отсутствующие значения обозначаются `н/д`; неполная стоимость не выдаётся за ноль.
Локальный токенизатор помогает сравнить контекст, но может расходиться с API.

Фактическое число генераций завершённого прогона без повторов:

| Стратегия | Основные ответы | Поддержка памяти | Проверка деталей | Итого сравнение | Отдельно ветвление |
| --- | ---: | ---: | ---: | ---: | ---: |
| Window | 12 | 0 | 10 | 22 | 12 |
| Facts | 12 | 12 | 10 | 34 | 16 |
| Summary | 12 | 3 | 10 | 25 | 12 |
| Все | 36 | 15 | 30 | 81 | 40 |

Ветвление — 4 обычных ответа, 6 проверок после переключений и 2 проверки checkpoint
на стратегию. Facts дополнительно обновляется 4 раза. Каталог модели и загрузка
токенизатора не являются генерациями и в эту таблицу не входят.

Основное сравнение включает **весь диалог + поддержку памяти + десять проверок**.
Ветвление посчитано отдельно. Дополнительно видны расходы только на проверки,
чтобы отделить размер запросов от накладных расходов стратегии.

Для сравнения объёма кода `complexity()` считает непустые строки классов памяти
без строк с одними комментариями. Для Facts и Summary включены строки базового
Window, от которого они наследуются. Общие Agent, Branches, клиент, промпты и отчёт
не входят в это число. Это прозрачная мера объёма реализации, не объективная оценка
трудности разработки. Обновление фактов и сводки также требует своих промптов и валидации.

## Файлы

- `agent.py` — три стратегии, Agent и независимые ветки.
- `main.py` — сценарий, HTTP-клиент, этапы запуска и проверки.
- `tokens.py` — токенизатор, сохранение метрик и сборка текстовых отчётов.
- `requirements.txt` — зависимости, как в дне 9.
- `results.txt` — создаётся при прогоне: реальные вопросы и ответы, изменения памяти
  и таблицы ответов с эталонами. Это читаемый текст, а не JSON-дамп.
- `metrics.txt` — создаётся при прогоне: попытки API, токены, стоимость и объём кода.

В `state/<strategy>/` локально хранятся полный журнал диалога для анализа,
checkpoint, рабочая память, файлы веток, ответы и usage. Каталог исключён из Git
через `.git/info/exclude` этой рабочей копии. В новом клоне перед прогоном добавьте
туда строку `/projects/day-10/state/`. Эти JSON-файлы не нужны в MR.

### Сохранность памяти и полнота ответов

Полным считаем ответ, передающий всю проверяемую деталь. «Только онлайн» соответствует
«только онлайн, без очного участия»; просто «онлайн на платформе» не подтверждает
отсутствие очного участия. Для материалов проверяем и один PDF, и отсутствие видео.
Частичный ответ содержит верную часть детали, но не все её ограничения.

| Стратегия | Деталей в доступной памяти из 10 | Полных ответов | Частичных | Не восстановлено |
| --- | ---: | ---: | ---: | ---: |
| Window | 2 | 2 | 1 | 7 |
| Facts | 10 | 10 | 0 | 0 |
| Summary | 10 | 8 | 2 | 0 |

Window сохраняет платформу и формат материалов. Сведения о формате «только онлайн»
уже вытеснены. Ответ «онлайн на платформе Контур.Толк» согласуется с оставшейся
платформой, но не доказывает память о договорённости. По одному ответу нельзя
установить, каким именно рассуждением модель к нему пришла.

У Summary оба частичных ответа относятся к данным, которые **присутствуют в памяти**:
сводка содержит «только онлайн, очного участия не будет», а несжатый хвост —
«одним PDF-файлом, без видео». Поэтому здесь наблюдаем неполноту ответа,
а не потерю этих ограничений при сжатии.

Facts содержит 13 ключей, представляющих все 10 проверяемых деталей. Время и часовой
пояс, а также онлайн-формат и отсутствие очного участия представлены раздельно.
Есть и избыточный ключ `подтверждение: да`: выделение фактов моделью не ограничивается
только полезными для проверки сведениями.

В Facts и Summary предварительные 30 000 рублей заменены утверждёнными 42 000;
обе стратегии правильно ответили о текущем бюджете. Среди десяти выбранных деталей
потерь в их сохранённой памяти не обнаружено. Это не проверка сохранности каждой
фразы диалога или поведения на произвольном числе обновлений.

содержат свои продолжения, у Facts — разные актуальные значения бюджета и срока.
Window верно использует новые договорённости, пока они находятся в его последних
сообщениях. Отсутствие исходных срока и бюджета у Window наблюдалось и до ветвления;
оно не является ошибкой изоляции веток.

В этих коротких ветках Summary не обновлялось: после checkpoint добавлено только
4 сообщения на ветку, порог — 10. Модель верно использовала новые значения из хвоста
вместо старых значений сводки. Пересечение порога обновления summary внутри ветки

### Выводы и выбор стратегии

- **Window** подходит, когда достаточно недавних сообщений и важны простота и
  ограниченный размер истории. В нашем прогоне он потребовал меньше всего токенов
  и верно отвечал о свежих договорённостях в ветках. Ранние детали удалены из окна,
  что следует из реализации ещё до API-прогона. Результат 2 полных ответа из 10
  означает недостаточность окна из 6 сообщений для данного сценария, а не плохое
  качество стратегии вообще.
- **Facts** имеет смысл для задач с конкретными договорённостями и параметрами,
  которые должны сохраняться независимо от давности сообщения. Здесь все десять
  деталей восстановлены полностью, исправления бюджета обработаны верно. Цена этого
  варианта — отдельное обновление после каждой пользовательской реплики; в нашем
  сравнении он оказался самым дорогим. Извлечение может сохранять и лишние данные,
  как ключ подтверждения в этом прогоне.
- **Summary** можно выбирать для продолжения разговора со сводкой старого контекста.
  Здесь все десять деталей присутствовали в памяти при меньшем расходе, чем у Facts,
  но два ответа оказались неполными. Нельзя объяснять эти пропуски потерями при сжатии:
  нужные ограничения сохранились. Превосходство summary для свободного обсуждения
  этим сценарием отдельно не проверялось.
- **Ветвление** работает независимо от выбора памяти: сохраняем и копируем состояние
  агента, затем загружаем нужную ветку. В проверенных переключениях данные A и B
  не смешались; исходные checkpoint сохранились.

Сценарий специально спрашивает о ранних конкретных деталях: восемь из десяти
оказываются за пределами короткого окна. Поэтому он проверяет последствия вытеснения
и сохранность альтернативной памяти, но не является универсальным рейтингом стратегий.
Для задач о текущем фрагменте разговора вывод о достаточности Window может быть другим.
Объём окна, частота обновлений и состав диалога здесь фиксированы; других настроек
и повторных прогонов для статистической оценки не было.
