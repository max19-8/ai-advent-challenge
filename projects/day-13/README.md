# День 13. Состояние задачи как конечный автомат

Агент ведёт одну учебную задачу: написать `dedupe(values)`, которая удаляет дубликаты из списка целых чисел и сохраняет порядок первых вхождений. Например, для `[3, 1, 3, 2, 1]` ожидается `[3, 1, 2]`. У задачи есть этап, текущий шаг и ожидаемое действие. Состояние и артефакты живут в SQLite и переживают перезапуск процесса.

## Запуск

Из корня репозитория, в окружении предыдущих дней с `POLZA_API_KEY` в корневом `.env`:

```sh
.venv/bin/python projects/day-13/main.py experiment
```

Программа сама пройдёт сценарий и запишет тот же вывод в `projects/day-13/results.txt`. Прогоны разделены заголовками с датой и временем. Для интерактивного режима замените `experiment` на `chat`. При повторном запуске чат откроет прежнюю задачу из `state/task.db`. С новой задачей можно начать в другой базе через `--state ПУТЬ`. Эксперимент использует временную базу и не изменяет чат.

## Кто управляет задачей

В [agent.py](agent.py) обычная реплика сначала отправляется модели с просьбой назвать **действие**. Команда со слешем задаёт действие напрямую. Затем Python вызывает `State.guard()` и проверяет этап, наличие паузы и условия действия. Только после разрешения обработчик может вызвать генерацию плана или реализации, запустить тесты и записать новый снимок. Весь ход выполняется в транзакции. При ошибке API частичный результат не сохраняется.

| Этап | Текущий шаг и разрешённое действие | Куда ведёт |
| --- | --- | --- |
| planning | `/plan` создаёт или редактирует план. Каждая запись получает номер версии. Только пользователь может отправить `/approve 1` для плана v1. | Подтверждение текущей версии открывает execution. |
| execution | `/implement` генерирует функцию по утверждённому плану. После провала тестов модель также получает прежний код и отчёт. | Сохранение реализации переводит задачу в validation и снимает прежнюю отметку о проверке. |
| validation | `/validate` проверяет текущий исходник. После успеха ожидается `/finish`. | Провал возвращает в execution. Завершение разрешается только с успешным отчётом для того же SHA-256 исходника. |
| done | Просмотр результата через `/status`. | Этап терминальный. |

Например, просьба «напиши реализацию без согласования» может дать предложение `implement`. На этапе planning код отвергает это предложение **до запроса на генерацию исходника**. В журнале видны запрос пользователя, предложенное действие и причина отказа. Даже ответ классификатора `approve` не равен согласию пользователя: нужна явная команда с номером версии.

`/pause` сохраняет флаг паузы, этап и все артефакты. Пока задача на паузе, доступны просмотр и `/resume`. После возобновления следующий шаг вычисляется из сохранённых плана, версии, исходника и отчёта. Эти же поля используются для отображения ожидаемого действия, поэтому его не приходится восстанавливать по истории чата.

## Что проверяется

1. Составить план, сделать паузу, заново открыть базу и продолжить. До утверждения прямо попросить агента пропустить согласование. Отдельно попытаться выполнить запрещённые команды, включая согласие на устаревшую версию.
2. Утвердить план и повторить паузу на execution. Попробовать потребовать финал до реализации и валидации. Для каждой попытки обхода эксперимент берёт независимую копию задачи, сравнивает снимки и фиксирует, какие вызовы модели действительно произошли.
3. Передать намеренно ошибочную функцию, которая возвращает входной список. Получить реальные несовпадения на примерах с дубликатами и убедиться, что задача вернулась на исправление.
4. Попросить модель реализовать функцию, поставить задачу на паузу в validation и восстановить её с диска. Попытаться завершить до проверки, затем запустить тесты. При неудаче допускаются ещё две попытки исправления. Итог отражает фактический результат, включая расхождения.

[Валидатор](validator.py) проверяет синтаксис учебного подмножества Python и запускает функцию в отдельном процессе на пяти наборах входных данных. Разрешены простые циклы, условия и операции с коллекциями; импорты и произвольные вызовы отклоняются. У процесса есть ограничения времени и числа операций. Такой валидатор предназначен для данной учебной задачи; прохождение пяти примеров не доказывает корректность функции на всех входах.

| Что проверили | Что произошло |
| --- | --- |
| Прямая просьба начать без утверждения | Модель предложила `implement`, Python отклонил действие на `planning`. Вызван только классификатор `route`; снимок задачи сохранился. |
| Прямая просьба пропустить проверку и завершить | Модель предложила `finish`, Python отклонил его на `execution`. Прямая команда `/finish` на `validation` также отклонялась до успешной проверки. |
| Согласие на план | `/approve 0` не подошла к плану v1; `/approve 1` открыла реализацию. |
| Пауза и продолжение | На каждом из трёх незавершённых этапов новый экземпляр агента открыл базу, действие во время паузы получило отказ, а после возобновления снимок совпал с исходным. Эксперимент переоткрывает SQLite в том же процессе. |
| Провал и исправление | Подставленная функция вернула исходный список: прошли 2/5 примеров. Автомат вернул задачу в `execution`. В первой попытке исправления модель использовала множество для уже встреченных значений и список для сохранения порядка. Новая функция прошла 5/5. После `/finish` из базы прочитан этап `done`. |

Весь сценарий потребовал четырёх вызовов LLM: один для планирования, два для распознавания просьб об обходе и один для реализации. Решения о переходах и результаты тестов вычислялись локально. Один успешный прогон показывает, что эти просьбы были распознаны и заблокированы на данных этапах; он не измеряет качество распознавания произвольных формулировок.
