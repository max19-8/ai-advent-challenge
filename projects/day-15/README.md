# День 15. Устаревание и конфликты памяти

Чат ведёт память выбранной задачи. Например, после реплик «Дедлайн — 12 декабря» и «Дату сдачи перенесли на 19 декабря» в актуальной памяти должна остаться одна дата. Журнал сохраняет обе даты и время замены.

## Запуск

Из корня репозитория при настроенных `.venv` и `POLZA_API_KEY` в корневом `.env`:

```sh
.venv/bin/python projects/day-15/main.py experiment
```

Эксперимент создаёт временную базу и дописывает вывод в `results.txt` рядом с программой. Для свободного диалога замените `experiment` на `chat`. Чат хранит SQLite в `state/memory.db`, стенограмму в `state/chat.txt`. Команды чата — `/task ИМЯ`, `/memory`, `/log`, `/finish`, `/exit`. После перезапуска можно выбрать прежнюю задачу через `/task` или `--task`.

## Как обрабатывается реплика

На обычную реплику приходится два вызова Qwen. Например, перед сообщением «Вместо подхода „Каскад“ выбираем „Пилот“» в базе стояло `approach = Каскад`. На первом вызове модель предложила операцию со значениями `kind=current`, `key=approach`, `value=Пилот`. В SQLite ей соответствует строка с ключом `(task, kind, key)`. Программа обновила эту строку, а в журнал добавила `REPLACE` с переходом «Каскад → Пилот». На втором вызове модель получила свежий снимок и подтвердила выбор. [Обработчик сообщения](assistant.py) · [Хранилище](memory.py)

1. Python фиксирует момент получения сообщения в UTC и порядковый номер. Qwen получает новую реплику и текущий снимок задачи. Для каждого изменения модель предлагает тип, стабильный ключ, значение. Чистый вопрос должен дать пустой список. Например, «дедлайн» и «дату сдачи» модель должна отнести к одному ключу `deadline`.
2. Python проверяет структуру всего пакета, типы полей и уникальность ключей. После успешной проверки изменения и записи журнала фиксируются в одной транзакции SQLite. Идентичность факта определяется задачей, типом и ключом. Приоритет определяется временем получения исходной реплики, при равенстве — порядковым номером. Запоздавшее обновление фиксируется как `IGNORE_STALE`.
3. Для ответа программа заново читает текущий снимок и отправляет его вместе с вопросом. Журнал замен и стенограмма остаются вне этого запроса. При подтверждении записи в запросе используются имена обновлённых полей. Если пользователь сам повторил прежнее значение в вопросе, буквальное совпадение маскируется, когда это значение больше нигде в задаче не актуально. Полный массив отправляемых сообщений печатается и записывается в отчёт. Если API ответа недоступен после записи, уже принятая поправка остаётся в базе.
4. Команда `/finish` очищает рабочие записи именно этой задачи и закрывает её для изменений. Долговременные факты, решения и журнал доступны после повторного открытия базы.

| Тип | Что происходит с данными |
| --- | --- |
| `current` | Срок, статус, версия, подход или другой изменяемый факт. По ключу хранится последнее значение с отметкой времени. |
| `decision` | Каждое независимое принятое решение добавляется под отдельным ключом. Исправление или отмена конкретного решения обновляет его запись. |
| `working` | Временные заметки, напоминания и черновики очищаются при завершении задачи. |
| Журнал | Каждое принятое изменение, подтверждение, очистка и запоздавшее обновление добавляются с прежним и поступившим значениями. |

Явная отмена сохраняет пустое значение и время. Благодаря этому запоздавшее сообщение не может вернуть отменённый факт. SQLite связывает событие с исходной репликой по номеру получения сообщения. Выбор правильного ключа и интерпретация смысла зависят от модели. Это отдельный чат для проверки памяти: источником контекста служат записанные факты, поэтому детали, которые модель не сохранила, могут быть утрачены.

## Что измеряет эксперимент

Обычными репликами пользователь задаёт исходные сведения, два самостоятельных решения и временную заметку. По очереди меняются срок, статус, требование и подход. Сразу после каждого изменения агент получает нейтральный вопрос. Для каждого из четырёх вопросов программа сверяет состояние базы, первый фактический ответ модели и весь запрос ответа. Старым считается буквальное упоминание одного из уже заменённых тестовых значений. Верный ответ должен совпасть с запрошенным кратким значением после нормализации регистра и пунктуации. Прочие ответы, включая многословные, выводятся отдельно. Проверка утечек определяет буквальные совпадения, семантические перефразировки требуют чтения протокола.

Далее программа завершает задачу, открывает базу заново, сравнивает сохранённые долговременные записи и спрашивает про временный пропуск и выбранный подход. Код выхода 2 означает, что сценарий завершился и нашёл расхождение, 1 — что прогон прервался.

```sh
.venv/bin/python -m unittest discover -s projects/day-15 -v
```

Локальные тесты проверяют порядок времени, равные отметки, поздние поправки после отмены, изоляцию задач, восстановление памяти, состав запроса и подсчёт ошибочных ответов. Результаты реальной модели определяются по `results.txt`.

Для продолжения прерванного эксперимента добавьте `--resume` к команде запуска. Программа сверяет завершённые ходы с журналом и сохранёнными промптами, восстанавливает их без API и продолжает с первой незавершённой реплики. Если в отчёте сохранился ответ извлечения на незавершённом ходе, программа повторно проверяет его локально. При неверной структуре изменений пакет отклоняется целиком, сценарий фиксирует ошибку и продолжает остальные проверки. Исходный текст сообщения сохраняет приложение.

## Результат эксперимента 22 ноября 2026 года

Qwen 2.5 72B Instruct дала четыре верных первых ответа после изменений — «19 декабря», «Согласован», «отменено», «Пилот». Устаревших ответов — 0 из 4. В четырёх полных промптах ответов было 0 буквальных совпадений с уже заменёнными тестовыми значениями. Контрольные вопросы не изменили память.

При завершении задачи число рабочих записей уменьшилось с 1 до 0. Все 6 долговременных записей сохранились вместе с отметками времени — четыре поля, включая отметку об отмене требования, и два независимых решения. После повторного открытия SQLite модель ответила «нет данных» на вопрос о временном пропуске и «Пилот» на вопрос о выбранном подходе.

Прогон продолжен через `--resume`. Десять завершённых ходов, включая первые три контрольных ответа, восстановлены из протокола. Извлечение поправки «Каскад → Пилот» также было сохранено. Четвёртый контрольный ответ и оба ответа после очистки получены от модели при продолжении. Приоритет по времени при запоздавшей записи проверяли отдельно локальным тестом.

## Выводы

| Изменение | Первый ответ на контрольный вопрос |
| --- | --- |
| 12 декабря → 19 декабря | 19 декабря |
| Черновик → Согласован | Согласован |
| Требование «Бумажный дубль» отменено | отменено |
| Каскад → Пилот | Пилот |

Сопоставление разных формулировок с одним ключом остаётся задачей модели. Если модель заведёт второй ключ для того же факта, сравнение времени внутри старого ключа не разрешит такой конфликт. В этом прогоне все четыре поправки попали в нужные записи.

Прерванные попытки показали отдельную проблему: повторное цитирование моделью зависело от оформления кавычек. Теперь Python привязывает изменение к оригиналу сообщения при получении. Эта связь устанавливает происхождение записи, а смысл извлечённого значения проверяется по протоколу.

В этом диалоге замену удалось проследить на каждом шаге. В журнале остались обе версии, в запрос ответа попало актуальное состояние, модель назвала новое значение. [Полный протокол](results.txt)
